## 0. 새 ChatGPT에게 — 먼저 읽을 것

우리는 Unity 6 URP 기반 **주술회전 캐릭터 선택형 3D 격투게임 `JJK_game`**을 장기 협업으로 개발한다. 사용자는 기획·최종 Play Mode 검수자, ChatGPT는 적극적인 기획 파트너·기술 리뷰어·레퍼런스 해석·Codex 프롬프트 작성자, VS Code Codex는 로컬 구현·테스트 담당이다. **사용자와 함께 게임의 재미를 고민하는 것이 목적**이며, 무조건 사용자 말에 동의하거나 질문 때마다 Codex 지시문부터 내밀지 않는다.

**현재 초점:** 시부야 기반 공통 전투 MVP를 상당 부분 개발·검수하고, PASS 4H에서 **흑섬 시각 연출 재설계** 중이다. 이전 3D 가지형 흑섬 REV1은 실제 전투에서 보존하면서, **새로 디자인한 키 포즈 4장 기반 L2 검은 파열 본체 + L3 붉은 경계 발광**을 QA 시제품으로 구현했다. 최신 L2/L3 targeted 검증은 단일 **3 PASS / 0 FAIL / 0 SKIP**다. 이후 관련 코드·원화·셰이더·테스트·문서 등 **66개 파일을 WIP 체크포인트 `cbfa138ed33523249a110bc44a5434dd245dde91`로 commit/push 완료**했다(2026-11-02). 저장 자체가 시각 최종 승인을 의미하지는 않는다. 사용자는 새 L2/L3 키 포즈/시각적 방향에 대해 **“와 확실히 좋아졌다..!!”**라고 긍정 평가했지만, **실제 로컬 MP4 전체를 ChatGPT가 독립적으로 감상·평가했다는 뜻이나 최종 흑섬 VFX의 USER VERIFIED / 실제 전투 교체 승인은 아니다.** 우선 시각 피드백·다음 시제품 범위를 협의한다.

**추천 Codex 모델을 잊지 말 것:** 보통 **GPT-6.1 Sol High**(해당 메뉴에 있으면); 원인 불명·아키텍처 난제·반복 실패 시 **Astra High / 필요한 경우 더 높은 추론** 검토. 명확한 문서·Git 검토는 Sol Medium이 충분할 수 있다. 모델 추천과 간단한 이유를 복붙용 프롬프트 **밖에 별도로** 적는다. 사용자가 Astra 사용 한도에 자주 걸려서 가급적 Sol 중심으로 개발하고 싶어한다. 실제 메뉴 접근성·성능·사용량을 확인하지 않고 단정 금지.

## 4. 협업·대화 규칙 — 이 프로젝트의 중요한 정체성

- **사용자 = 기획자·최종 의사결정자·실제 플레이 검수**, **ChatGPT = 창의적 기획 파트너·기술 리뷰어·레퍼런스 큐레이터·Codex 명세 작성·인수인계 담당**, **VS Code Codex = 로컬 구현·자동 테스트·문서 갱신**.
- 통상 흐름: `아이디어/레퍼런스 → 여러 안 비교 → 사용자와 규칙 합의 → Codex 복붙 지시문 → Codex 구현/자동검증 → ChatGPT 결과 비판적 검토 → 사용자 Play Mode → USER VERIFIED 승인(범위 제한) → 명시적 요청 시 선택적 commit/push → 다음 PASS`.
- 사용자가 **의견**을 물으면 계획·대안·리스크를 논의. 사용자가 구현을 요청했을 때에만 Codex 프롬프트를 작성하며 매 질문마다 프롬프트부터 길게 내밀지 않는다.
- **표현 방식:** 한국어·친근한 협업 말투(가벼운 ㅋㅋㅋ 가능). 무조건 칭찬하지 않고 논리적인 반론·대안·구체적 이유를 제시. 잘 모르는 개발 용어는 짧은 뜻 + JJK_game 예시로 설명.
- **레퍼런스·그림이 중요한 답변:** 가능하면 실제 게임/애니 이미지·영상/공식 자료를 찾아 보여주고 어떤 장면이 어떤 장점이 있는지 설명한다. 1~2개의 말만 적지 말고 원작의 구도/타이밍/움직임을 관찰해 **우리 게임에 적용할 아이디어와 한계를 함께 제시**. 사용자 첨부 영상은 실제로 열어보지 않았으면 봤다고 하지 않는다. 사라진 다른 채팅의 파일은 자동 접근 가능하다고 가정하지 않는다.
- 이미지·영상은 **이해를 돕기 위해 사용**하되, 참조 이미지와 실제 구현 결과 및 자체 생성 콘셉트를 명확히 구분한다. 영상 링크가 `D:\...`이면 ChatGPT는 사용자의 로컬 파일을 직접 열 수 없다. 첨부된 자료를 분석하면 정지 프레임뿐 아니라 **원속도·느린 속도·시점별 차이**를 구분해 평가한다.

### 표준 행동 명칭과 입력

- **지상:** 기본 콤보, 업 콤보, 다운 콤보, 주력 회복(=F 홀드 주력 충전), 가드, 가드브레이크, 패링, 잡기, 반격, 스킬1(`Q`), 스킬2(`E`), 스킬3(키 미정), 궁극기 또는 각성(`R`, 캐릭터별 단계형 R 가능), 주력 대쉬, 대쉬(`C`). Q/E/R의 캐릭터별 표시명은 기술 이름(예: `Q(주력 강화 펀치)`)으로 표현.
- **공중:** 공중 콤보, 공중 스킬. 향후 신규 기능은 새 이름 협의.
- 사용자가 나중에 잘못된 명칭이나 옛 키를 말하더라도 **현재 표준 명칭의 의미를 우선 이해**하되, 실제 입력 충돌이 있으면 현재 코드/대화로 확인. 과거 문서의 `Z=각성`, `W=스킬2`, `Space=고죠 Dodge`를 현 시부야 조작 확정값으로 사용하지 않음. `W/S`는 **지상 4타 분기**에 여전히 사용되고, Space는 시부야에서 점프·업 추격·다운 탈출 상황별 의미가 다름. `Space=회피`는 이전 별도 고죠 VFXLab 입력이다.
- 공격 분류 메타데이터는 **도달(근접/원거리/특수) × 성격(체술/술식/복합) × 출처(평타/스킬/반격/궁극기/기타)**를 독립적으로 다룬다. 모든 원거리 공격을 흑섬 가능으로 처리하지 않는다. 캐릭터별 흑섬 자격과 실제 적격 타격 이벤트가 모두 필요하다.

## 7. 현재 핵심 — PASS 4H 흑섬 VFX의 긴 시행착오와 방법론 변화

### 7.1 왜 개발 방법을 바꿨는가

- 초창기 흑섬은 프레임 캡처의 검은 획을 **3D 분기 메시**로 해석해 만든 결과 실제 원속도에서 검붉은 **가시 공·나뭇가지·거미 다리**처럼 보였다.
- Gemini 및 ChatGPT 기술 자문을 Codex가 실제 코드와 비교: REV1은 **33개 연결 획**, 가지 스케일 확대와 뿌리→끝 공개 동시 적용, 주가지 약 **103ms**·늦은 지류 약 **143ms** 완성, 이른 부분 소거도 약 **191ms 이후**. 원인은 **형상 + 성장 방식 + 불투명 표면 유지**의 복합 문제. '시간 문제가 90%' / '모든 3D 메시가 실패'라는 단정은 기각.
- A/B/C 기술 방식(3D/플립북/2.5D+3D), BASE/T(성장 시간 95→30ms)/S(형상)/TS(둘 다) 비교 실험 수행: 시간만 줄이면 **더 빨리 나오는 나무**, 형상만 바꾸면 **검은 판·갈고리**, 조합해도 시각 정체성 근본 개선은 부족. 기술 PASS를 예술적 PASS로 취급하지 않는 교훈.
- 렌더 분석 도구 **Unity Frame Debugger**는 비전면 API로 시도했으나 GPU 이벤트를 확보하지 못했다고 보고. 실제 프레임 디버거 분석 성공이라고 기록 금지. **RenderDoc**은 3D 메시/셰이더/그리기 순서를 더 자세히 볼 수 있지만 당시 미사용. **REA(Reverse Engineer Anything)**는 기존 우리 게임에 소스코드가 있어 당장 필요하지 않음. 타사 상용게임 역공학 범위/권한과 내부 원본 복원 가능성을 과장하지 않는다.

### 7.2 새로운 미술 기준과 L0~L6 레이어

사용자가 만족한 **새 시각 목표 인포그래픽(Visual Target)**이 있다. 경로는 사용자가 정리한 **`D:\JJK_game\_local_refs\videos\blackflash_refs\`** 한 폴더로 통일하고, 원본 영상 `로블_흑섬.mp4`, `주팬퍼_흑섬.mp4`, 승인 콘셉트 그림은 `흑섬_레이어.png`라는 파일명으로 Codex가 발견했다고 보고했으며, 실제 파일 상태는 로컬에서 재확인한다. `images\blackflash` 별도 폴더를 정답으로 주장하지 않는다.

- **L0:** Impact Frame(화면 반전/흑백·짧은 플래시). **일반 흑섬에도 극히 짧게 사용하기로 한 사용자 방향이며**, 확정 필살기/특수 컷인 흑섬은 강화. '선택적'은 현재 L2/L3 QA 시제품에 아직 포함하지 않았다는 작업 순서로만 해석. 실제 프레임 타이밍은 추후 플레이 테스트로 조정.
- **L1:** 타격점 코어 플레어(짧고 강한 흰빛).
- **L2:** Main Black Mass — 주인공. **넓은 검은 먹물 파열**, 비대칭·날카롭게 찢어진 실루엣, 긴 획 일부 유지, 작은 파편은 별도 해체. 단순 별/포털/나무/거미/고체 판처럼 보이지 않음.
- **L3:** Red Edge Glow & Slashes — **매우 중요: 사용자 최종 의도는 붉은 에너지가 검은 파열 실루엣의 외곽을 따라가는 것**이다. 전체 외곽을 따라도 되며 두께/밝기는 불규칙, 별도 튀는 붉은 방전도 가능. 예전 AI의 '외곽 일부만 강조'를 **고정 규칙으로 쓰면 안 됨**.
- **L4:** 소수의 고속 압력선·날카로운 광선(보조; 방사형 별빛 과다 금지).
- **L5:** 검은 파편·흑먼지·소량의 환경 먼지/연기(타격 본체 가리지 않음).
- **L6:** 본체 소멸 후 짧은 붉은 방전·검은 잔광·잔사.
- 인포그래픽 약 **0.30초 시간표는 디자인 예시이지 검증된 원작 절대값 아님**. 0.01~0.03초 L0/L1, 0.03~0.08 L2, 0.08~0.15 L3/L4, 0.15~0.25 L5, 0.25~0.30 L6 등을 출발점으로 실험하되 실제 원속도 체감으로 조절.

### 7.4 VFX 제작 방법의 영구 개선 — 최우선 협업 규칙

**이 프로젝트에서 가장 큰 개선:** 완성형 이펙트를 코드로 만들고 일부 정지 프레임으로 자기 합격을 선언하는 방식을 버린다.

**기본 흐름:**
1. **원본 영상 정상 속도 관찰**(동작의 첫인상·의미) → 필요한 부분 0.5/0.25배속·연속 프레임으로 검증. 원본 내부 FPS 추정과 녹화본 FPS 구분.
2. **형태/시간/질감/렌더링 계층 분해**, 제작 방식은 검증되지 않은 가설로 유지. 번개처럼 보여도 실제 3D 가지라고 단정 X.
3. **Art direction 먼저:** 실제 참조·원작 시각 목표/승인된 콘셉트 → 검은 실루엣 **키 포즈 이미지**와 레이어 타임라인. 전문가가 아닌 사용자도 합격·수정 판단하기 쉽게 **그림으로 설명**.
4. **독립 QA 시제품**: 핵심 레이어 우선, 동작/형태를 원속도로 비교. 같은 카메라·거리·피격점·난수·밝기·전체 규모. 전투 VFX·잠금값은 그대로.
5. **L2 본체만 / L3 테두리만 / L2+L3 / 전체 / REV1** 레이어별 격리 및 정면·측면·45도·360도 카메라에서 영상 촬영. 일시 정지 모양뿐 아니라 **재생 시 느낌**을 평가.
6. **코드 시간축·메시·머티리얼/렌더 순서와 영상의 차이를 대조**. 필요시 Unity Frame Debugger/RenderDoc을 고려하되 실제 조작·캡처했는지 구분. QA 수치로 예술적 유사도가 자동 증명되지 않음.
7. **제작 AI와 비평 AI를 구분:** 만든 사람이 '성공' 선언하지 말고 원본/결과 영상의 현상·위화감·예측 실패를 독립적으로 평가. 자체 비평의 한계를 기록, 인간(사용자) 최종 미술 승인.
8. **시각 디자인 합격 후** 코어 광/압력선/잔류/카메라 충격·반전·오디오를 점진적으로 통합. 화려한 추가 레이어가 부족한 본체를 가리지 않게 한다.
9. 새 VFX/스크린샷은 결과가 **실제 플레이 화면에서 읽히는지** 최종 확인. 사용자 '좋아졌다' = 해당 방향성 칭찬일 수 있어 전체 최종 완료와 구분.

**기술 선택 중립:** 3D 메시, 2D 알파 플립북, 다층 2.5D, VFX Graph, Particle System, Shader Graph, Distortion/Full Screen 효과를 목적에 맞게 조합. **3D 전체 폐기·플립북 무조건 정답** X. 주력 아우라, 무라사키처럼 모델이 이미지에서 시간감·깊이감을 잘못 추론하지 않도록 실측 영상 비교를 습관화.

## 9. USER VERIFIED와 테스트 정확성

- **USER VERIFIED** = 사용자가 Unity/Blender에서 직접 플레이·화면·손맛을 보고 **특정 범위**에 한정해 승인한 것. 사용자가 “통과”, “잘 된다”라고 한 기능 범위만 적용. VFX가 임시라고 하면 최종 미술 승인 X.
- **CODEX VALIDATED(targeted)** = Codex가 수행한 국소·기술적 검사 성공. 영상·테스트가 있어도 사용자의 아트 디렉션 최종 승인을 뜻하지 않는다.
- **LOCAL UNCOMMITTED** = 사용자의 PC에서만 진행, GitHub에는 없음. 원격이 clean이어도 로컬 WIP가 존재할 수 있다.
- **복수 실행 최신 고유 케이스 집계** ≠ **단일 전체 테스트 PASS**. 최초 실패·고쳐진 테스트·Console/Shader/Pipeline 오류·미실행 테스트 구분하여 보고.
- commit/push는 **명시적 사용자 요청 후에만**, 승인한 파일만 선택적 staging, staged diff 확인, 일반 push 후 로컬·원격 HEAD 일치 확인. dirty `.slnx` 등 사용자 변경은 보존. 체크포인트 작업에서 이미 통과한 Unity 테스트를 이유 없이 재실행하지 않는다.

## 12. 1) 추후 게임 계획 — GAME

### GAME-01 — 플레이 루프와 캐릭터 선택 [방향 합의/추후]

- **목표:** 시부야/신주쿠 같은 넓은 도시를 배경으로 하는 **자유 카메라·자유 이동 3D 주술회전 격투게임**. 초기에는 **싱글 1:1/훈련/VS 봇**부터 손맛을 완성하고 장기적으로 자유 난전·다인전·온라인으로 확장한다. 나루티밋 스톰의 오의 연출을 참고하지만 전투 카메라를 항상 1:1 고정시키지는 않는다. 게임 비전 문서의 1:1 우선과 시부야 설계의 장기 난전은 단계가 다른 목표로 병존한다.
- **메뉴 초안:** 메인 메뉴 `게임 시작 / 캐릭터 / 옵션` → 게임 시작 → 시부야 입장 후 실제 출전 캐릭터 선택 → 전투 → 승패·재도전/메뉴 복귀. 메인 메뉴의 캐릭터 화면은 **도감·능력 설명**, 출전 선택과 다른 역할. 전투 중 임의 캐릭터 변경·태그 및 자동 리스폰은 현 방향에 없음.
- **미완성:** 실제 메뉴 흐름·온라인 모드·대전 규칙과 저장 데이터는 별도 설계·검증 필요. `Custom/Ranked` 등은 후보일 뿐 확정 구현 아님.

### GAME-02 — 캐릭터별 고유 체술·무브셋 [방향 합의/추후]

- **핵심:** 고죠가 고정 주인공이 아니다. 유지·스쿠나·유타·메구미·마키·토도 등 캐릭터마다 **콤보 타수, 공격 중 전진/후퇴/추적, 공중 연계, 고유 패시브, 술식, 잡기·반격·피격 모션**까지 달라야 한다. 블록 캐릭터는 공통 엔진 검증 도구이며 최종 애니메이션 품질 목표가 아니다.
- **중요한 과거 결정:** **한 번의 좌클릭에 여러 실제 타격 이벤트**가 들어갈 수 있다. 공격자 이동·상대 넉백·회전·자동 접근은 각각 별도 Data Asset 값으로 조절. 특정 캐릭터의 순간이동·위치 교환은 그 공격 무브셋의 일부일 수 있고, 독립 대시로 무조건 분류하지 않는다. 토도의 부기우기처럼 실제 교환하면 원래 자리로 자동 복귀시키지 않는다.
- **상태:** 공통 지상4타·업/다운 분기·공중 추격/공격은 MVP 수준 구현·승인, **캐릭터별 완성 3D 모션은 아직 별도 작업**. 발동하지 않은 기술에 무제한 적 추적·벽 관통·확정 타격을 주지 않는다.

### GAME-03 — 도시 맵·제한적 환경 파괴 [방향 합의/추후]

- **맵:** 시부야 교차로·도로·건물 외관으로 먼저 싸울 공간 확보. 추후 신주쿠형 전장, 지하·내부·옥상, 넓은 도시 구역 확장을 검토. 전투 맵은 모듈화하되 첫 버전에 전 도시를 완성하지 않는다.
- **파괴:** 일반 체술도 강도에 따라 유리·얇은 벽·일부 콘크리트를 손상하거나 뚫을 수 있는 방향. 약한 충돌=먼지·균열, 강한 충돌=제한된 벽 파괴·관통, 특수 술식=전용 환경 반응. 직접 술식 파괴와 날아간 적의 환경 충돌 파괴는 별도 원인으로 다룬다.
- **사용자 선호:** **파괴 흔적은 그 전투가 끝나거나 맵이 초기화될 때까지 남음. 자동으로 몇 초 뒤 복원하지 않음.** 초기 구현은 미리 지정한 파괴 가능 조각만 사용. 도시 전체를 물리 시뮬레이션으로 부수는 방식은 초기 범위 아님. `벽 바운스`는 당초 초안에서 제외하고 저항/파괴 방향을 선호했으나 추후 실전 검토 가능.
- **혼동 금지:** 현재 다운 착지의 일시적인 바닥 균열은 위의 **지속형 환경 파괴 구현이 아니다**.

### GAME-04 — 훈련 AI·대전 재미 [구현/USER VERIFIED 범위 제한 + 추후]

- 초기에는 실제 도시 지형 파괴보다 `decal / mesh / particles` 등의 **presentation-only scar**로 검증 가능. 기존 경로·데미지·시전 타이밍은 임의 변경하지 않는다.
- 기존 과거 외피 VFX R&D의 검은 질량과 Final2 기준도 보호하고, 실험 후보의 유리/수정 조각처럼 보이는 문제를 개선할 때 사용자가 검수한 좌/우 표기를 정확히 확인.

### VFX-05 — 무량공처 공간·검은 구체·터널 [방향 합의/추후, 기존 기준 보호]

- **보존:** 기존 사용자가 만족했던 보라색 라인 터널, 푸른 성운·검푸른 우주 깊이감, 보이지 않는 게임플레이 바닥, Domain 상태·기본 전투 기능.
- **외부 검은 구체:** 고죠와 실제 포획된 대상을 빠르게 감싸는 연출. 크기·닫히는 시간·불투명도는 **사용자용 한국어 Inspector에서 튜닝**, 다만 게임플레이 포획 판정 반경과 동일시 금지.
- **내부 목표:** 360도 어디를 봐도 실제 다른 영역 내부라고 느껴야 함. 한쪽 큰 원형 이펙트에 모든 효과가 몰린 문제를 개선. 완전 검은 중심의 블랙홀/코스믹 아이, 불규칙한 경계, 근·중·원거리 깊이의 흰 피/액체/먹물 같은 파열, 3박자로 등장하는 흰 효과, 캐릭터가 읽히는 푸른·보랏빛 중간톤. 평면 흰 구름이나 한쪽 빌보드만 추가하지 않음.
- **시각 목표와 실제 구현**을 구분하고, 현재 PASS4H 흑섬 개발의 직접 범위로 섞지 않는다. 영역의 카메라/포획/내부 공간 규칙은 DOMAIN 항목 참고.

### VFX-06 — 공통 타격·공간·환경/사후 잔류 [방향 합의/추후]

- 기준은 원작의 술식 정체성 + Strikeborn급 이상의 **임팩트 밀도와 타격감**. 기술마다 무조건 같은 링/번개/파티클을 붙이는 것이 아니라 예고→형성→발사→이동→충돌→환경 반응→잔류→카메라·화면→소리의 **필요한 beat를 조립**.
- 빠른 보통 타격과 묵직한 막타·흑섬의 충격 세기 구별. 실제 공격 접촉/데미지, 애니메이션, 국소 히트스톱, 카메라, SFX, 피격 모션, 환경 반응을 같은 시각 이벤트로 혼동하지 말고 동기화.
- 레퍼런스 출처와 실제 관찰 사실/엔진 구현 가설을 구분. 게임 원본 모델·텍스처·상용 asset을 무단 복제/임포트하지 않음.

## 14. 3) 영역전개·시네마틱 계획 — DOMAIN

### DOMAIN-01 — 반드시 서로 다른 세 공간 [방향 합의/추후 + 기존 아키텍처 보호]

1. **Gameplay Capture Radius:** 기존 도시 맵에서 영역 시전 시 **누가 잡히는지 결정하는 실제 판정 반경**.
2. **Visual Barrier Radius / Diameter:** 도시 맵에서 **검은 구체가 얼마나 커 보이는지**. Inspector에서 크기 자유 조절. 포획 판정과 다른 값.
3. **Domain Interior Space:** 장벽 구체 내부 크기에 1:1로 종속되지 않는 **별도의 광대한 포켓 공간/맵**. 단순한 하늘 텍스처 교체로 해결했다며 끝내지 않음.

영역 진입에서 기존 위치·방향·카메라·필요한 참가자 전투 상태를 안전하게 기록하고 종료/취소 시 정확하게 복원. 초창기 고죠 P0의 DOMAIN ACTIVE 중 이동/기본공격/회피 및 종료 후 복구는 기승인 보호 대상.

### DOMAIN-02 — 고죠 무량공처 오의형 카메라 [구체적인 사용자 구상/추후]

**목표:** Naruto Ultimate Ninja Storm / Sparking! ZERO처럼 **기술의 실제 성공 여부에 따라 달라지는 짧은 영화적 컷신**. 원작 영상을 그대로 복제하라는 뜻은 아님.

- **발동 기준:** 실제 포획된 적이 **1명 이상**이면 긴 피해자 중심 시네마틱. 잡힌 적이 **0명**이면 고죠/영역만 찍는 짧은 버전.
- **대표 피해자 선정:** 여러 명이 잡혔을 때 `포획된 lock-on 대상 우선 → 가장 가까운 포획 적 → 안정적인 fallback`. 선택 대상은 카메라 주연일 뿐 실제 영역 효과는 포획된 **모든 적**에게 적용.
- **권장 샷:** ① 손/영역 장인 근접 → ② 안대를 내리는 고죠 측면 얼굴 → ③ 육안(Six Eyes) 초근접 → ④ 고죠 정면 영웅 샷·장인 → ⑤ 고죠/피해자 검은 구체 폐쇄 와이드 → ⑥ 보라색 터널 이동·피해자 중심 → ⑦ 피해자의 얼굴·허공 응시·경직 클로즈업/측면 → ⑧ 검은 블랙홀과 흰 피 같은 다층 파열 → ⑨ 360도 영역 내부 공개 후 정상 카메라 복구.
- **제작 현실:** 안대 해제 애니메이션이 없으면 억지로 메시를 늘리지 않고 애니메이션 훅을 마련. 피해자 표정은 얼굴 rig/blendshape 준비 전에는 `고개 방향/정지 자세/상체/카메라 각도`로 대체. 새로운 캐릭터가 나와도 재사용 가능한 시네마틱 샷 데이터 구조 선호.
- **소유권:** 공격자/피격자 참가자에게만 임시 카메라 override. 제3자 카메라와 전투는 계속. 사망·영역 취소·씬 전환·연출 중단·Preview 반복 시 shake/FOV/follow/target 등 **원래 카메라 상태 정확히 복구**. 전역 `Time.timeScale` 정지 금지.
- **참조:** 2026-09-08 최초 인수인계의 `7~11장`에 더 세밀한 샷 언어가 있다. 20초경의 셀/거품 이미지는 당시 사용자 요청으로 **모방 대상에서 제외**.

### DOMAIN-03 — 영역 파괴 및 외부 구조 [명시적 보류]

**당장 하지 않기로 결정:** 검은 구체의 barrier HP, 외부 동료 공격으로 장벽 파괴/구출, 외부·내부 동시 전투 및 결계 파괴 체계. 현재는 장벽 표현과 포획·영역 내부 소유권을 분리해 향후 확장 가능성만 보존한다.

### DOMAIN-04 — 다른 캐릭터 영역·영역 충돌 [장기 목표/미확정]

영역의 완성도·발동속도·범위·필중 조건·개방형 결계·강화 상태·술사 현재 자원, 다인 동시 전개/충돌을 향후 Data/Trait 기반 규칙으로 설계. 원작의 영역 정체성과 상성은 살리되 **'영역 먼저 누른 사람이 무조건 승리' 또는 숫자 한 개로 결정**하는 안은 피하고 싶다는 기획. 실제 다자 동기화/수치/미니게임 방식은 별도 합의 필요.

## 15. 4) 전투 규칙·캐릭터 차별화 — COMBAT

### COMBAT-01 — 공격 분류와 특수 방어 [기존 분류 구현 + 미래 초안]

- 구현된 기본 공격 메타데이터는 `도달(근접/원거리/특수) × 성격(체술/술식/복합) × 출처(평타/스킬/반격/궁극기/기타)`로 별도 분리. **흑섬 가능 여부는 캐릭터 자격 + 해당 타격 자격 + 실제 유효 피해**를 함께 확인.
- **미래 특수 방어 초안:** 고죠 Infinity의 상시 차단, 영역전연의 접촉/생득술식 제한·주력 비용, 간이영역의 필중 대응, 신카게류 발도의 조건부 반응, 천역모·흑승의 무효/교란. `대상 추적 → 적중 여부 → 특수 방어 → 실제 피해·피격 → 치명/흑섬/Zone 결과`를 섞지 않는 구조를 검토. **무하한 완전 차단이라면 피해·피격 모션·경직이 없어야 한다는 방향**.
- 위 세부 무효화 스킬들의 **지금 실제 구현 여부와 상성·밸런스는 미확정**. 다음 작업을 자동 착수하지 않는다.

### COMBAT-02 — 가드·패링·잡기·탈출·기동 [현재 MVP 보호 + 추후]

- 현재 사용자는 기본 가드/패링/잡기/방향 대시/긴급 기상을 승인했지만, 방어막·패링·잡기 **최종 VFX·모션**과 완전한 밸런스를 승인한 것은 아니다.
- 가드 체력은 HP·주력과 별도; **기본 HUD에 수치 바로 공개하지 않고 시각 피드백으로 위험 표현**. 잡기는 가드를 무시하는 별도 옵션이며, 나중에 캐릭터별 연속타·던지기·짧은 잡기·카메라 연출이 달라질 수 있음. 현재 15HP/1.4m는 공통 임시값.
- 패링은 타이밍에 맞는 **새 RMB 입력**이 중요, 일반 가드/반전술식 더블탭/잡기와 입력 충돌·우선순위를 캐릭터별 스킬 확장 시 재검토. 성공 후 자동 반격 X; **0.5초 안에 새 LMB로만 반격 선택**(현재 기준).
- 대시: 카메라 기준 `WASD+C`, 전방은 접근용 무적 없음. **과거 2026-10-20 인수인계에는 후방 대시 무적 없이 재검토하자는 의견이 있지만, 이후 2026-10-30 잠금 문서는 측면·후방 무적구간 0.04~0.14s를 기록**. 이 불일치를 임의 해결하지 말고 **최신 코드·사용자 직접 확인**을 우선. 기존 승인값 무단 수정 금지.

### COMBAT-03 — 흑섬·Zone·주력·신체 강화 [현재 MVP 보호 + 추후]

- **현재 보호 수치(기본 구현값):** 주력 최대200, F 회복 기본12/초, 치명타25%×1.5, 흑섬×2.5(치명타와 곱셈 중첩 X), 흑섬 일반/Zone 최종 상한15%/20%, 반격 자격 시 별도50% 조건부, 유효 흑섬 보상 주력+10·스택+1·Zone12초. Zone 피해+10%·소비-15%·F 회복+20%, 중첩 아님. 흑섬 능력 기본OFF. **코어/수치 변경 요청이 없다면 그대로**.
- 흑섬 시각 VFX의 품질이 낮다고 해서 확률·피해·Zone·캐릭터 유효 자격까지 뜯어고치지 않는다.
- **신체 강화 패시브는 사용자 결정으로 보류**: 준비·해제 임팩트, 강화 중 아우라, 공격력·이동속도 강화, `W+F` 기반 주력 대시 등은 아직 구현된 기능이 아님. 기존 F 아우라가 주력 회복량200 때문에 비대해지지 않도록 시각 기준 용량 보존.

### COMBAT-04 — 반전술식·각성·장기 캐릭터 고유 규칙 [아이디어/재논의]

- 반전술식(RCT)은 사용할 수 있는 캐릭터만, 큰 주력 소모·재생 조건·시전 시 취소 가능성 등을 가진 고유 능력. 오래된 입력 초안의 `빠른 RMB 두 번`은 가드/패링/잡기와 충돌하므로 **현재 확정 조작으로 가정 금지**.
- 각성은 주력과 별도 게이지, 수동 발동, 캐릭터별 활성 단계·지속시간·재충전 제한 등 구상. **옛 설계의 Z=각성, Q/E/R 3술식은 현재 표준 키로 덮어쓰기 금지**. 현재 표준은 스킬1 Q, 스킬2 E, 스킬3 키 미정, 각성·궁극기 R(세부 발동 방식 추후 합의).
- 무주력 천여주박(토지·마키), 개방 영역 스쿠나, 리카/카피 유타, 적응 마허라 등은 단순 캐릭터명 조건문이 아니라 Trait/Passive/TargetPolicy 기반 데이터로 표현하는 장기 구상.

## 16. 5) UI·사운드·연출·리소스 — PRESENT

### PRESENT-01 — HUD·UI·키 바인딩 [장기 목표, 일부 HUD는 현재 구현]

- **기획 방향:** 하단 중앙에 캐릭터 얼굴·기술 슬롯·HP(초록)·주력(파랑), 옆 세로 각성 게이지, 버프/디버프와 남은 시간. 스킬 이름과 아이콘·쿨타임은 캐릭터별. 가드 체력은 시각적 방어막으로만 힌트. 상대 HP의 상시 표시 방식, HUD 크기/키 설정 및 옵션은 후속 UX 설계.
- 현재 표준 슬롯 `Q/E/스킬3 키 미정/R`과 옛 `Q/E/R + Z`를 **동일한 확정 설정으로 혼합 금지**. 전투 중 ESC/옵션 진입 동작도 예전 제안 단계.
- 로컬 Gojo VFXLab의 `Space=회피`와 시부야 공통 전투의 `Space=점프/추격/기상`는 씬과 상태가 다르다.

### PRESENT-02 — 캐릭터 음성·애니메이션 연동 [방향 합의/추후]

- 최종 기술은 스킬 키만 누르면 즉시 폭발하는 것이 아니라 **캐릭터 고유 동작 → 음성 → 발사 순간 → 실제 판정/VFX**가 맞아야 한다. 예: Red 손끝 핵 수렴·시전 자세·'아카' 발화 후 release cue; 무량공처 안대 내림·육안·장인·대사·구체 포획.
